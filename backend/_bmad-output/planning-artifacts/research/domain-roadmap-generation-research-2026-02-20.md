## AI Planning Techniques for Roadmap Generation

### Hierarchical Task Decomposition Frameworks

The most relevant architectural pattern for roadmap generation is **hierarchical decomposition** — breaking a high-level goal into progressively finer-grained subtasks.

**HiPlan (Hierarchical Planning for LLM Agents)**
Generates a global "Milestone Action Guide" that decomposes tasks into sequential and interconnected subgoals. This dual-level guidance (global milestones + local steps) enables agents to advance toward goals in a more focused and error-averse manner, leading to higher success rates and markedly shorter trajectories. **This directly maps to monthly milestones → weekly steps.**
_Source: [arXiv - HiPlan](https://arxiv.org/html/2508.19076)_

**GoalAct (NCIIP 2025 Best Paper)**
Introduces a continuously updated global planning mechanism integrated with a hierarchical execution strategy. Decomposes task execution into high-level skills to reduce planning complexity while enhancing adaptability. Key innovation: maintaining a global plan that updates as execution proceeds, rather than planning once up front.
_Source: [arXiv - GoalAct](https://arxiv.org/abs/2504.16563)_

**ADaPT (As-Needed Decomposition and Planning)**
A recursive algorithm that decomposes tasks into sub-tasks only when necessary. Employs separate planner and executor LLM modules. When the executor fails on a task, the planner decomposes it further. Achieved success rates 28.3% higher on ALFWorld, 27% higher on WebShop, and 33% higher on TextCraft vs. baselines.
_Source: [arXiv - ADaPT](https://arxiv.org/abs/2311.05772)_

**STEP Planner**
Leverages a foundation LLM to break down complex goals into manageable subgoals, spanning a hierarchical tree structure from coarse to fine resolutions.
_Source: [arXiv - STEP Planner](https://arxiv.org/html/2506.21030)_

**ACONIC (Constraint-Based Decomposition)**
Models a task as a constraint problem and leverages formal complexity measures to guide decomposition, providing a principled way to determine where to split complex tasks.
_Source: [arXiv - ACONIC](https://arxiv.org/abs/2510.07772)_

### Planning Paradigms

**Chain-of-Thought (CoT)**
Guides the model to reason step-by-step. Foundational for sequential plan generation but falls short for tasks requiring exploration, strategic lookahead, or where initial decisions heavily influence outcomes.
_Source: [IBM](https://www.ibm.com/think/topics/chain-of-thoughts)_

**Tree-of-Thought (ToT)**
Generalizes CoT by maintaining a tree of "thoughts" with search algorithms (BFS, DFS) for systematic exploration with lookahead and backtracking. In Game of 24, GPT-4 with CoT solved only 4% of tasks, while ToT achieved 74%. Applicable when multiple roadmap structures need to be explored and compared.
_Source: [NeurIPS 2023](https://proceedings.neurips.cc/paper_files/paper/2023/file/271db9922b8d1f4dd7aaef84ed5ac703-Paper-Conference.pdf), [IBM](https://www.ibm.com/think/topics/tree-of-thoughts)_

**Graph of Thoughts (GoT)**
Represents reasoning as a graph — each node is a thought, edges are dependencies. Allows merging nodes to create more complex thoughts. 62% improvement in sorting quality and 31% cost reduction vs. ToT. Best suited for tasks that decompose into subtasks solved individually and then merged.
_Source: [AAAI](https://ojs.aaai.org/index.php/AAAI/article/view/29720/31236)_

**Plan-and-Execute Architecture**
Separates planning from execution. A Planner LLM creates a multi-step plan, and separate Executors handle each step. Benefits: (a) forces explicit thinking through all steps, (b) allows smaller/cheaper models for execution, (c) faster since the planner is not consulted after each action.
_Source: [LangChain Blog](https://blog.langchain.com/planning-agents/), [LangGraph Tutorial](https://langchain-ai.github.io/langgraph/tutorials/plan-and-execute/plan-and-execute/)_

**Plan-and-Solve Prompting**
Two phases: (1) Plan Formulation — LLM analyzes the problem and creates a plan, (2) Plan Execution — LLM works through each subtask in sequence. Prompt template: *"Let's first understand the problem and devise a plan to solve the problem. Then, let's carry out the plan and solve the problem step by step."*
_Source: [arXiv](https://arxiv.org/abs/2305.04091), [ACL 2023](https://aclanthology.org/2023.acl-long.147.pdf)_

### Self-Improvement & Verification Techniques

**Self-Refine (Madaan et al.)**
Three-stage iterative loop: GENERATE → FEEDBACK → REFINE. The same LLM acts as generator, critic, and refiner. No supervised training data or RL required. Improved task performance by ~20% absolute on average across 7 diverse tasks. GPT-4o-mini improves assertion correctness by 21.76 percentage points through self-refinement.
_Source: [selfrefine.info](https://selfrefine.info/), [arXiv](https://arxiv.org/abs/2303.17651)_

**Reflexion**
Agents verbally reflect on task feedback signals, maintaining reflective text in an episodic memory buffer. Architecture: Actor (generates), Evaluator (scores), Self-Reflection (generates verbal cues for improvement). Improves decision-making by 22% absolute, reasoning by 20%.
_Source: [PromptingGuide](https://www.promptingguide.ai/techniques/reflexion), [arXiv](https://arxiv.org/abs/2303.11366)_

**CISC (Confidence-Improved Self-Consistency)**
Weighted majority voting based on confidence scores, prioritizing high-confidence reasoning paths. Outperforms standard self-consistency, reducing required reasoning paths by over 40%.
_Source: [ACL Anthology](https://aclanthology.org/2025.findings-acl.1030/)_

**Multi-Agent Judge-Planner Architecture**
Externalizes critique into an independent Judge + Planner system. GPT-4-mini achieved 80% recall and 93% precision in plan verification.
_Source: [arXiv](https://arxiv.org/html/2509.02761v2)_

**MIT LLMFP Framework**
Achieved 85% success rate on complex planning challenges (vs. 39% baseline). Asks the LLM to detail requirements, encode them into mathematical optimization formulation, then write code calling an optimization solver.
_Source: [MIT News](https://news.mit.edu/2025/researchers-teach-llms-to-solve-complex-planning-challenges-0402)_

## Context Retrieval & Prompt Engineering

### Context Retrieval: Vector Search vs. SQL for Intake Data

**Key Finding: Simple SQL queries are the right choice for structured intake data. Vector search is not appropriate.**

For structured questionnaire data (known schema, typed fields, relational joins), direct SQL retrieval is almost always the correct approach:

- **SQL excels at structured data management**, thriving on exact matches and well-defined conditional logic. For exact match queries, SQL with proper indexing is very fast, while vector search is slower.
  _Source: [OpenAI Community](https://community.openai.com/t/structured-data-semantic-search-sql-or-text-to-sql-or-vector-search/844405)_

- **Vector databases are "great at vibes but terrible at math or structured logic."** They are poor at structured/semi-structured queries and limited in analytics and aggregations.
  _Source: [DigitalOcean](https://www.digitalocean.com/community/tutorials/beyond-vector-databases-rag-without-embeddings)_

- For data with **little semantic value that would benefit from vectorization** (e.g., structured survey responses, numeric scales, multiple choice answers), SQL-like databases handle queries efficiently.
  _Source: [Towards Data Science](https://towardsdatascience.com/when-not-to-use-vector-db/)_

- The **QASU benchmark** for questionnaire analysis found that diverse serialization formats (CSV, JSON, XML) influence LLM parsing — but embeddings are not part of the recommended approach. Direct serialization into the prompt is recommended.
  _Source: [arXiv - QASU](https://arxiv.org/html/2510.26238)_

**Cross-encoder reranking is also overkill** for structured intake data. Since you know exactly which records to fetch (by user_id and goal_id), there's no relevance ranking needed.
_Source: [Pinecone](https://www.pinecone.io/learn/series/rag/rerankers/)_

### Long Context vs. RAG

For a single user's intake data (a few KB at most), the data fits easily in the context window:

- **Long-context models match or beat RAG** on most benchmarks when data fits in the window. RAG's retrieval step is lossy — chunking splits at arbitrary boundaries, and top-K selection discards potentially relevant passages.
  _Source: [arXiv](https://arxiv.org/html/2501.01880v1)_

- The **LaRA benchmark (2025)** with 2326 test cases found that when data fits inside a single context window, **long context gives equal or better recall**, provided documents are structured with clear delimiters and metadata headers.
  _Source: [arXiv - LaRA](https://arxiv.org/abs/2502.09977)_

**Recommendation:** Fetch intake Q&A via SQL, serialize as structured JSON/text, inject directly into the LLM prompt. No RAG, no embeddings.

### Prompt Engineering for Structured Plan Output

**Prompt Structure Best Practices:**
- Use the formula: **Role + Task + Context + Constraints + Output Format + Tone**
- Provide user questionnaire answers as structured data in the user message; use system message for persona, format, and constraints
- Specify section structure, JSON schema, length, and what each section should contain
  _Source: [Palantir](https://www.palantir.com/docs/foundry/aip/best-practices-prompt-engineering), [Garrett Landers](https://garrettlanders.com/prompt-engineering-guide-2025/)_

**Prompt Chaining for Progressive Detail:**
Break plan generation into logically connected stages: (1) generate high-level milestones, (2) expand each milestone into weekly steps. Context retention through intermediate outputs improves coherence.
_Source: [Orq.ai](https://orq.ai/blog/prompt-structure-chaining), [Deepchecks](https://www.deepchecks.com/orchestrating-multi-step-llm-chains-best-practices/)_

**Few-Shot vs. Zero-Shot:**
- **Few-shot (1-2 examples)** is superior for structured plan generation — teaches the desired JSON format through examples
- However, with **schema-enforced structured outputs** (OpenAI Structured Outputs, or schema validation), zero-shot becomes viable since the schema itself constrains the format
- Practical recommendation: use few-shot with 1-2 examples of desired plan structure for best results
  _Source: [Shelf](https://shelf.io/blog/zero-shot-and-few-shot-prompting/), [MLMastery](https://machinelearningmastery.com/zero-shot-and-few-shot-learning-with-reasoning-llms/)_

**Structured Output Enforcement:**
- **OpenAI Structured Outputs** strictly enforces adherence to a specified JSON schema via `response_format` or function calling with `strict: true`
- **OpenRouter supports structured outputs** — directly relevant to Momentum's tech stack
- **Production pipeline:** Prompt → Generate → Validate → Repair → Parse. Set temperature to 0 for deterministic decoding.
  _Source: [OpenAI](https://platform.openai.com/docs/guides/structured-outputs), [OpenRouter](https://openrouter.ai/docs/guides/features/structured-outputs)_

**Reliability Hierarchy for Structured Output:**
1. Tool/Function Calling with `strict: true` — guarantees schema and syntax (best)
2. Few-Shot prompting — teaches schema through examples
3. Output Priming — nudges syntax through hints (e.g., starting with `{`)
   _Source: [IBM Developer](https://developer.ibm.com/articles/json-prompting-llms/)_

### Hallucination Mitigation in Plans

- Combine: (a) structured prompt design with explicit constraints, (b) domain-specific validation rules, (c) grounding in user's actual constraints from intake data
- Prompt-based mitigation alone lowered hallucination rates from 66% to 44% overall, and from 53% to 23% for GPT-4o
- For plan generation: provide explicit lists of valid actions, timeframes, and user constraints as variables in the prompt
  _Source: [MDPI](https://www.mdpi.com/2073-431X/14/8/332), [Wiley](https://advanced.onlinelibrary.wiley.com/doi/10.1002/adrr.202500072)_

## Coherence & Consistency Strategies

### Logical Sequencing and Dependencies

**DAG-Based Plan Representation:**
LLMs can convert natural language procedures into structured Directed Acyclic Graphs (DAGs), capturing both logical and temporal dependencies between tasks. Planners output plans as JSON schemas or task graphs specifying dependencies, tools, and success criteria.
_Source: [arXiv](https://arxiv.org/pdf/2504.00029)_

**LiP-LLM:**
Integrates dependency graph generation using LLMs with task allocation via linear programming, ensuring tasks with order constraints execute in the appropriate sequence.
_Source: [arXiv](https://arxiv.org/html/2410.21040v1)_

**Brain-Inspired Modular Architecture (Nature Communications):**
A modular agentic architecture where LLMs handle specific planning functions in isolation but are coordinated by an overarching system. Addresses the finding that LLMs struggle with multi-step reasoning when left unstructured.
_Source: [Nature](https://www.nature.com/articles/s41467-025-63804-5)_

### Ensuring Realistic Pacing

**Grounding with Constraints:**
Google Research's trip planning work grounds LLM-generated itineraries with real-world constraints (timing, capacity), then uses optimization to find feasible schedules. For goal planning: ground with user's stated time commitment, effort level, and experience from intake.
_Source: [Google Research](https://research.google/blog/optimizing-llm-based-trip-planning/)_

**Hybrid LLM + Optimization:**
MIT LLMFP encodes planning requirements into mathematical optimization formulations, combining LLM qualitative reasoning with constraint-solving to ensure feasibility.
_Source: [MIT News](https://news.mit.edu/2025/researchers-teach-llms-to-solve-complex-planning-challenges-0402)_

**Known Limitation:**
LLMs are less reliable at quantitative logistical constraints requiring detailed, real-world information. Plans may include impractical elements without external grounding. This reinforces the need to inject user constraints (available hours/week, effort level) explicitly.
_Source: [Interloom](https://www.interloom.com/en/blog/reliable-planning-with-llms), [Communications of the ACM](https://cacm.acm.org/blogcacm/can-llms-really-reason-and-plan/)_

### Iterative Refinement for Plan Quality

**Self-Refine Loop:**
GENERATE → FEEDBACK → REFINE (all same LLM). ~20% average improvement in quality. For roadmap generation: generate initial plan, then ask the LLM to critique it for logical gaps, pacing issues, and dependency violations, then refine.

**ISR-LLM (Iterative Self-Refined LLM):**
Three-stage cycle: Initial Generation (CoT/few-shot) → Validation/Diagnosis → Targeted Refinement of minimum necessary output. Loop persists until validator finds no errors or max iterations reached.
_Source: [ISR-LLM Paper](https://events.infovaya.com/uploads/documents/pdfviewer/07/da/129529-0239.pdf)_

## Goal Decomposition Frameworks

### Backward Planning (Academic Gold Standard)

Research shows backward planning is **superior to forward planning** for goal achievement:

- **Compared with forward planning, backward planning led to greater motivation, higher goal expectancy, less time pressure, and better goal-relevant performance** (Park, Lu, & Hedgcock, 2017, Psychological Science)
- Backward planning requires imagining goal achievement first, making it feel closer in time, and helping think of required tasks **more clearly, especially when goals are complex**
  _Source: [PubMed](https://pubmed.ncbi.nlm.nih.gov/28910234/), [Qz](https://qz.com/work/1094759/the-order-in-which-you-plan-makes-a-difference)_

### SMART Goals Framework

The foundational methodology: **Specific, Measurable, Achievable, Relevant, Time-bound.** Break sub-tasks into milestones tied to specific subtasks. Eliminates generalities and guesswork, sets clear timelines, makes progress tracking easier.
_Source: [Atlassian](https://www.atlassian.com/blog/productivity/how-to-write-smart-goals), [Smartsheet](https://www.smartsheet.com/blog/essential-guide-writing-smart-goals)_

### OKR (Objectives and Key Results)

An Objective (qualitative) with 2-4 Key Results (measurable). Can be combined with **WBS (Work Breakdown Structure)** to transform abstract goals into actionable task networks, dissecting annual goals into quarterly/monthly/weekly task units.
_Source: [Atlassian](https://www.atlassian.com/agile/agile-at-scale/okr), [ATableList](https://www.atablelist.com/blog/en/b4a79251_df5b_41c7_b0f5_b39bab90be9c)_

### Work Breakdown Structure (WBS)

The project management gold standard for hierarchical decomposition:
- **3 or 4 levels** — from project goal to major deliverables, sub-deliverables, and work packages
- **Branches need go only to the level of detail necessary** for effective management
- Can be more detailed on immediate work, summary on future work
  _Source: [PMI](https://www.pmi.org/learning/library/work-breakdown-structure-basic-principles-4883), [ProjectManager](https://www.projectmanager.com/guides/work-breakdown-structure)_

### Temporal Granularity: Monthly Milestones + Weekly Steps

- **Recommended 5-10 milestones** for a typical project — enough granularity to track progress meaningfully without excessive overhead
- Planning intervals: **weekly for short-term objectives, monthly for ongoing initiatives, quarterly for strategic objectives**
- **Weekly check-ins** assess progress and allow adjustments; **monthly reviews** evaluate milestone achievement
  _Source: [Monday.com](https://monday.com/blog/project-management/project-milestones/), [Leantime](https://leantime.io/goals-vs-milestones-leantime/)_

### The 12 Week Year Framework

Treats 12 weeks as your "year." Create a vision, reverse-engineer into 12-week goals, write weekly execution plans, commit to daily MITs. **Shortened timeframes push individuals to prioritize more effectively, reduce procrastination, and maintain urgency.**
_Source: [12weekyear.com](https://www.12weekyear.com/), [LogRocket](https://blog.logrocket.com/product-management/12-week-year-approach/)_

### Locke & Latham Goal-Setting Theory (35+ Years of Research)

- **High and specific goals lead to better performance** than low/non-specific goals (400+ studies)
- **Proximal goals lead to better performance than distal goals**, mediated by increased self-efficacy
- Performance errors on dynamic tasks are often due to **deficient decomposition of a distal goal into proximal goals**
- Five principles: **Clarity, Challenge, Commitment, Feedback, Task Complexity**
  _Source: [Stanford](https://med.stanford.edu/content/dam/sm/s-spire/documents/PD.locke-and-latham-retrospective_Paper.pdf), [ResearchGate](https://www.researchgate.net/publication/254734316_Building_a_Practically_Useful_Theory_of_Goal_Setting_and_Task_Motivation_A_35Year_Odyssey)_

### GROW Coaching Model

**Goal, Current Reality, Options, Will/Way Forward.** Provides a structured framework for setting goals, assessing the current situation, exploring solutions, and committing to action. The intake questionnaire maps naturally to the "Current Reality" and "Options" stages.
_Source: [MindTools](https://www.mindtools.com/an0fzpz/the-grow-model-of-coaching-and-mentoring/)_

## Personalization Strategies

### Profile-Based Personalization

- When an LLM distills user information into a specific profile in memory, this has the **greatest impact on personalization**
- MIT research found personalization features make LLMs more agreeable and responsive to individual needs
- **Dynamic user profiles** should evolve over time based on interactions
  _Source: [MIT EECS](https://www.eecs.mit.edu/personalization-features-can-make-llms-more-agreeable/), [arXiv](https://arxiv.org/html/2504.14225v2)_

### USER-LLM Framework (Google Research)

Distills diverse user interactions into user embeddings, contextualizing the LLM via cross-attention or soft-prompting. Achieves **12-21.9x reduction in FLOPs** compared to text prompt baselines, with performance improvements up to 16.33%.
_Source: [Google Research](https://research.google/blog/user-llm-efficient-llm-contextualization-with-user-embeddings/)_

### Adaptive Learning Path Generation (EdTech Patterns)

Transferable patterns from education technology:
- **Knowledge Graph + Reinforcement Learning**: Construct a knowledge graph unifying resources, use RL to dynamically generate personalized learning pathways
- Systems incorporate **user profile modules** capturing cognitive, sensory, and behavioral profiles
- **Adaptive algorithms** analyze performance data to identify knowledge gaps, create personalized paths, recommend content, and adjust difficulty levels
  _Source: [Springer Nature](https://link.springer.com/article/10.1007/s44217-025-00908-6), [ScienceDirect](https://www.sciencedirect.com/science/article/pii/S2666920X25000694)_

### Encoding User Constraints into Plan Generation

- Use the **Role + Task + Context + Constraints + Output Format + Tone** prompt formula
- A hybrid approach of strong system prompts, lean user requests, and light post-processing yielded the most practical path to spec-compliant generation (tested across 18 leading LLMs)
- Anthropic emphasizes **context engineering** — designing the entire environment in which an AI model thinks and acts
  _Source: [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), [Palantir](https://www.palantir.com/docs/foundry/aip/best-practices-prompt-engineering)_

### Intake-Driven Personalization

- AI tools can analyze intake form data and produce **personalized onboarding** that acknowledges specific challenges mentioned by the client
- **Pre-session prompts** can generate discussion guides based on stated goals and current challenges
- **Structured memory architecture** — the system reads its own notes from previous sessions, creating week-over-week continuity
  _Source: [Arsturn](https://www.arsturn.com/blog/developing-an-ai-coach-prompt-engineering-for-personalized-guidance), [Action Potential](https://www.actionpotential.co/p/building-a-coach-that-remembers-you)_

### Context Window Optimization

- **Avoid context bloat** — performance degrades significantly as context length increases; don't fill the window unnecessarily
- For structured intake data: retrieve only the relevant Q&A pairs, not everything
- **Summarization, dynamic retrieval, and strategic memory** help manage context
  _Source: [16x Engineer](https://eval.16x.engineer/blog/llm-context-management-guide), [DataCamp](https://www.datacamp.com/blog/context-window)_

## Multi-Stage LLM Generation Pipelines

### Recommended Architecture: Two-Stage Plan-and-Execute

The most directly applicable architecture for generating roadmaps:

**Stage 1 — Milestone Generation (Planner)**
- Use a capable model (e.g., Grok 4.1, Claude Sonnet 4.6) to generate high-level monthly milestones
- Input: serialized intake Q&A data + goal profile + user constraints (effort level, experience, target deadline)
- Output: structured JSON array of milestones with titles, descriptions, expected outcomes, and temporal ordering
- Apply backward planning — start from the goal and work backwards

**Stage 2 — Step Expansion (Executor)**
- For each milestone, generate detailed weekly steps
- Can use the same or a smaller/cheaper model
- Input: milestone context + overall goal + user constraints
- Output: structured JSON array of weekly steps with specific actions, expected outcomes, and tips

**Optional Stage 3 — Self-Refine**
- Feed the complete plan back to the LLM for coherence review
- Ask it to identify: logical gaps, pacing issues, dependency violations, unrealistic steps
- Refine based on feedback
- ~20% quality improvement on average

### Chaining Multiple LLM Calls

- **Sequential chains** break tasks into subtasks, where output of one iteration becomes input for the next, enabling **progressive refinement**
- Intermediate steps involve summarization, hypothesis generation — each step utilizes previous output as input, augmented with additional context
- **Hierarchical planning + prompt chaining** reduces hallucination and optimizes reasoning
  _Source: [Mirascope](https://mirascope.com/blog/llm-chaining), [Orq.ai](https://orq.ai/blog/prompt-structure-chaining)_

### Cost Optimization with Cascaded Models

- Use a capable model for Stage 1 (milestone generation — critical for quality)
- Use a faster/cheaper model for Stage 2 (step expansion — more constrained, less creative)
- Amazon Science research confirms: **task decomposition with smaller LLMs can make AI more affordable** while maintaining quality
  _Source: [Amazon Science](https://www.amazon.science/blog/how-task-decomposition-and-smaller-llms-can-make-ai-more-affordable)_

### Scientific Evaluation Baseline

The Nature Scientific Reports 2025 paper benchmarking LLMs for structured task flow generation found: **structured prompting strategies (especially domain-guided ones) significantly outperform zero-shot approaches.** The introduced Hybrid Semantic Similarity Metric (HSSM) combines SentenceTransformer embeddings with context-aware key-term overlap to measure both semantic fidelity and procedural coherence.
_Source: [Nature Scientific Reports](https://www.nature.com/articles/s41598-025-19170-9)_

## Key Recommendations for Momentum

### 1. Context Retrieval
**Use simple SQL queries via Supabase.** Fetch intake Q&A by `user_id` + `goal_id`, serialize as structured JSON, inject directly into the LLM prompt. No vector search, no RAG, no embeddings needed. The data is structured, small, and you know exactly what to retrieve.

### 2. Goal Decomposition Approach
Apply **backward planning** (academically proven superior). Use a **3-level WBS-inspired hierarchy**: Goal → Monthly Milestones (5-10) → Weekly Steps per milestone. This aligns with the 12 Week Year framework, SMART goals, and Locke & Latham's finding that proximal subgoals lead to better performance.

### 3. Generation Architecture
Use a **two-stage Plan-and-Execute pipeline**:
1. **Stage 1 (Milestones):** Strong model generates high-level monthly milestones from full intake context using backward planning
2. **Stage 2 (Steps):** Same or cheaper model expands each milestone into weekly steps
3. **Optional Stage 3 (Self-Refine):** LLM reviews the complete plan for coherence, pacing, and dependency issues (~20% quality improvement)

### 4. Prompt Engineering
- System prompt: role (expert goal coach), output format (JSON schema), constraints (use ONLY user's stated constraints)
- User prompt: serialized intake Q&A data + goal profile + deadline
- Use **few-shot with 1-2 examples** of desired plan structure, OR leverage OpenRouter's structured output support
- Apply the **production pipeline**: Prompt → Generate → Validate → Repair → Parse

### 5. Coherence & Personalization
- Inject user constraints (effort level, available time, experience) as explicit variables — not buried in prose
- Use backward planning prompt structure to ensure milestones build logically
- Apply Self-Refine loop for coherence verification
- Ground plans in user's actual constraints to minimize hallucination (reduces hallucination from 53% to 23% for GPT-4o)

### Key Technical Decisions

| Decision | Recommendation | Confidence | Rationale |
|----------|---------------|------------|-----------|
| **Context retrieval** | Simple SQL queries via Supabase | Very High | Structured data, small volume, known keys — vector search adds complexity without benefit |
| **RAG / embeddings** | Not needed | Very High | Intake data fits easily in context window; long-context outperforms RAG when data fits |
| **Generation approach** | Two-stage pipeline (milestones → steps) | High | Mirrors HiPlan architecture; reduces hallucination; enables cost optimization |
| **Planning direction** | Backward planning (goal → milestones) | High | Academically proven superior: more motivation, higher expectancy, better performance |
| **Structured output** | JSON schema enforcement via OpenRouter | High | OpenRouter supports structured outputs; guarantees parseable format |
| **Prompt strategy** | Few-shot (1-2 examples) + schema | High | Few-shot superior for structured output; schema provides additional safety net |
| **Self-refine loop** | Optional Stage 3 | Medium | ~20% quality improvement but adds latency and cost; evaluate via A/B testing |
| **Model selection** | Strong model for Stage 1; same or cheaper for Stage 2 | Medium | Planning quality is critical; step expansion is more constrained |
| **Milestone count** | 3-10 based on goal timeframe | High | Industry standard: 5-10 milestones for meaningful progress tracking |
| **Step granularity** | Weekly | High | Proximal goals > distal goals (Locke & Latham); weekly check-ins are industry norm |

### Prompt Engineering Blueprint

**System Prompt Structure:**
```
Role: Expert goal achievement coach with [domain] expertise
Task: Generate a structured roadmap using backward planning
Constraints:
  - Use ONLY the user's stated constraints (effort, time, experience)
  - Each milestone must build on previous ones
  - Weekly steps must be specific and actionable
  - Respect the user's target deadline
  - Ensure progressive difficulty increase
Output Format: [JSON schema definition]
```

**User Prompt Structure:**
```
Goal: {goal.title} — {goal.description}
Target Deadline: {goal.target_deadline}
User Constraints:
  - Effort Level: {from intake}
  - Available Time: {from intake}
  - Experience Level: {from intake}
  - Key Challenges: {from intake}

Intake Context:
{serialized Q&A pairs as structured JSON}

Generate a roadmap with monthly milestones working backward from the deadline.
```

### What Competitors Teach Us

1. **None use purely generative single-shot planning** — all augment LLMs with domain knowledge, templates, or proprietary data
2. **Noom's 4-stage pipeline** (instruction → RAG augmentation → dynamic user data → JSON output) is the closest public architecture reference
3. **BetterUp's moat** is 17M behavioral data points, not the LLM — validates that domain data is the differentiator
4. **Dreamfora uses template matching**, not pure generation — suggests that having a knowledge base of proven plan patterns improves quality
5. **Safety/escalation should be a separate system** — don't burden the plan generation model with crisis detection
6. **JSON structured output is universal** — confirmed by Noom, OpenAI, OpenRouter as the standard

### Applicable Goal Decomposition Frameworks

For Momentum's roadmap generation, the most applicable frameworks to encode into prompts:

1. **Backward Planning** — Start from goal achievement, work backwards to identify what must happen each month
2. **SMART Criteria** — Each milestone and step should be Specific, Measurable, Achievable, Relevant, Time-bound
3. **WBS (Work Breakdown Structure)** — 3-level hierarchy: Goal → Monthly Milestones → Weekly Steps
4. **Locke & Latham Principles** — High/specific goals, proximal sub-goals, progressive challenge increase
5. **GROW Model** — Map intake data: Goal (from goal record), Reality (from intake answers), Options (AI generates), Way Forward (the roadmap)

### Risks and Mitigations

| Risk | Mitigation |
|------|-----------|
| Hallucinated/unrealistic steps | Ground in user constraints; explicit constraint injection; Self-Refine loop |
| Poor pacing | Backward planning distributes work from deadline; encode effort level |
| Generic/cookie-cutter plans | Deep personalization from intake Q&A; few-shot with domain-specific examples |
| Inconsistent JSON output | Schema enforcement via OpenRouter; validate → repair → parse pipeline |
| High latency (multi-stage) | Roadmap generation is a one-time operation per goal (not real-time); acceptable |
| Cost per generation | Use cheaper model for Stage 2; cache few-shot examples; batch milestone expansion |
